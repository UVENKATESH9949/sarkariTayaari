Not engineering unknowns — each of these needs an answer from a business or technical owner before it should be treated as settled. See [TICKET-STATUS.md](./TICKET-STATUS.md) for what's built, [../memory/STATUS.md](../memory/STATUS.md) for what's next in priority order.

| Whether the admin console has any authentication | No, as of 2026-08-17 — now fixed. Role-based admin accounts (ADR-009): `users.role` (`STUDENT`/`ADMIN`), every content-management endpoint now requires `requireAdmin()`, first admin via `AdminBootstrapRunner` startup config, further admins via `POST /api/auth/admin/register`. | Cloud provider / hosting for the production backend | **Google Cloud Run**, region `asia-south1`, as of 2026-08-21. Live at `https://sarkaritaiyaari-backend-815653276881.asia-south1.run.app`, verified serving real content from Neon. Scale-to-zero with `--max-instances=3` to stay inside the free tier, accepting a ~10-20s cold start. Reuses the existing Neon database by explicit decision. See `reports/14-cloud-run-deployment/cloud-run-deployment.md`. |
| How release APKs get built and signed | **GitHub Actions**, as of 2026-08-21, chosen by the user after reviewing the alternatives (scripted local, containerized, generic CI, mobile-specialist CI like Codemagic/Bitrise, and Expo's own EAS Build). A real RSA-4096 upload keystore now exists outside the repo; signing survives `expo prebuild` via an Expo config plugin, since Expo's template hardcodes the debug key and offers no property-driven release config. `versionCode` comes from `github.run_number`. Retention is deliberately two-tier: a 30-day artifact per push to `main`, a permanent GitHub Release per `v*` tag. An `apksigner` signer-fingerprint check fails the build if the APK isn't signed by the upload key. See `reports/15-github-actions-apk-builds/github-actions-apk-builds.md`. **Update 2026-08-24: proven — run #4 completed successfully on GitHub and produced a real signed APK artifact, confirmed via the Actions API.** Play Console submission (TICKET-505's other half) is still separately open. |
| Whether the app holds up at 10,000+ questions (TICKET-501) | Mostly, with real caveats — as of 2026-08-19 (round 2). ~37,900 questions across 11 active exams now exist (pushed further per user request, toward V1.2's TICKET-701 20k-50k target). A full sync pass takes ~236s server-side at this scale (up from ~118s at 14k, consistent scaling, not a regression). Four real backend performance bugs (bulk-import, progress-sync, batch-fetch-size, bookmark-sync) plus one mobile-side bug (unbatched SQLite writes hanging sync indefinitely) were found and fixed across both rounds. The mobile fix was re-verified at ~2.7x its original scale (round 1 fixed it at 14k; round 2 confirmed it still holds at 37,900, with a real device-side timed delta sync completing without crash or hang). The demo account now has 350 practice sessions / 85 mock attempts (confirmed via server-side restore; on-device restore was only directly re-verified at the round-1 scale, not re-checked after round 2 due to an emulator UI-interaction snag with the sign-out button). See `reports/12-load-test-data-seeding/load-test-data-seeding.md`. |
| Whether the app should keep a blocking first-launch gate, and what it should wait for | **Keep the screen, cap it at 5 seconds, and change what it gates on** — decided by the user 2026-08-27, resolving a direct conflict between a supplied requirements prompt (remove the blocking screen entirely) and the deliberately-built, art-directed `PreparingApp` screen. The substantive change is that the gate currently waits for the whole **question** sync; it should wait only on **reference data** (8 small requests), with questions moved to background work and covered by the existing `useHybridMode()` live fallback. A hard 5-second ceiling enforced independently of sync state becomes a safety net rather than the normal path, and **fixes the offline first-launch lockout by construction**. The progress bar advances smoothly and monotonically toward release, never showing 100% early — but must not print a synthetic "N / M questions" count beside a time-smoothed bar; measured figures stay on the More screen. Full design: `offline-exam-app-requirements.md` §9.5. |
| Whether the app holds up with the full question bank served (no temporary pool) | **Yes, verified end to end 2026-08-27.** `app.question-pool.temporary-enabled` is now `false` and all **37,884** questions sync to the device. A full sync is 76 pages, ~2.7s/page server-side (≈203s server time, consistent with the ~236s in `reports/12-load-test-data-seeding/`) — but that cost is now invisible: the first-launch gate releases on reference data before any question page is written, and the app is fully navigable while the remaining 75 pages download. A 136-question quiz loads without error. The prerequisite work (`getPracticeQuestions` `LIMIT`, the `loadSessions` N+1, six new indexes, list virtualization) landed first, per §9.4's required ordering. |
| Retry/backoff policy for failed syncs | **Indefinite retry with exponential backoff** (2s base, doubling, capped at 30s), as of 2026-08-24 — `runInitialSyncUntilDone()` wraps the existing per-page-checkpointed sync, so a retry resumes at the next page rather than restarting. Built in direct response to a real user-reported production failure (intermittent 500s from the deployed backend partway through a sync). The likely server-side root cause (Cloud Run has no explicit `--memory` allocation) was diagnosed but deliberately **not** fixed — this closes the client-side resilience gap, not the backend's. See `reports/17-resilient-initial-sync/resilient-initial-sync.md`. |
