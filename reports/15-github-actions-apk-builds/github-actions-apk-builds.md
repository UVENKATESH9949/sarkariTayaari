# GitHub Actions APK Builds

**Closes:** the user's explicit request for a repeatable, self-serve APK build ("I want
some dynamic", i.e. not driven by an AI session each time), and **half of TICKET-505** —
the real signing keystore and signed-build pipeline now exist; the Play Console
internal-testing track does not. Also replaces the distribution mechanism ADR-006 flagged
as not production-final, and which `reports/14-cloud-run-deployment/` recorded as
effectively dead once the backend moved to Cloud Run (`/downloads` serves from local disk,
which on Cloud Run is ephemeral and scales to zero).

Scope was chosen by the user after being shown the full landscape of build-automation
approaches (local scripted, containerized, generic CI, mobile-specialist CI, EAS Build)
across four independent layers — build environment, trigger, signing, distribution. They
picked GitHub Actions.

## What existed before

Confirmed by reading the repo and the machine, not assumed:

- **No workflows at all.** `.github/` contained only `modernize/java-upgrade/hooks/`
  scripts, unrelated to CI.
- **A `Jenkinsfile` with a real `Mobile — APK` stage** — correct in shape (prebuild, then
  `assembleRelease`), and the source of the sequence reused here. No Jenkins instance is
  known to be running, and it has no deploy or signing stage.
- **Release builds were debug-signed**, stated plainly in `README.md`: *"Release builds
  are currently signed with the debug key… it cannot go to the Play Store, and a debug key
  regenerated on another machine produces a signature mismatch that blocks
  upgrade-in-place."*
- **No keystore existed anywhere** on the machine or in the repo.
- **`versionCode` was hardcoded to `1`** — `app.json` has no `android.versionCode`, so
  `expo prebuild` emitted the default. Every build produced the same version code.
- **`mobile/node_modules` was empty**, and `mobile/android/` held a stale build tree from
  an earlier session.
- **A machine-level `~/.gradle/gradle.properties` already existed**, written after an
  earlier Android build exhausted this 16 GB box's commit limit and got the daemon killed
  (`Native memory allocation (malloc) failed`). It caps daemon heap at 3 GB, disables
  parallelism, limits workers to 2, and runs the Kotlin compiler in-process. This turned
  out to matter — see "Real bugs found".

## What was built

**`mobile/plugins/withReleaseSigning.js`** — an Expo config plugin, the load-bearing piece.
`android/` is not committed and is regenerated by `expo prebuild` on every build
(Continuous Native Generation), so nothing edited inside it survives. Expo's SDK 57
template hardcodes `signingConfig signingConfigs.debug` in the release buildType and —
unlike the bare React Native template — offers **no** property-driven release
`signingConfig` to hook into. A config plugin runs *during* prebuild, so it is the only
durable place to make this change. The plugin:

- inserts a `release` entry into `signingConfigs { … }` that reads four Gradle properties
  (`ST_UPLOAD_STORE_FILE`, `…_STORE_PASSWORD`, `…_KEY_ALIAS`, `…_KEY_PASSWORD`);
- rewrites the release buildType to select that config when the properties are present,
  and otherwise fall back to the debug key **with a loud `logger.warn`**, so the existing
  local `./gradlew assembleRelease` convenience keeps working;
- is idempotent via a `sarkaritaiyaari:release-signing` marker;
- **throws** rather than silently skipping if either template anchor is missing, because a
  silent skip produces a debug-signed APK that looks completely normal.

Exports the pure `injectReleaseSigning` transform, and requires `expo/config-plugins`
lazily, so the transform is testable without `node_modules`.

**`mobile/app.config.js`** — dynamic layer over `app.json`, which stays the human-edited
source of truth and is passed in as `config`. Supplies `android.versionCode` from
`ANDROID_VERSION_CODE` (default `1`), an optional `versionName` override, and registers the
signing plugin in code rather than as an opaque path in a JSON array.

**`mobile/scripts/check-release-signing-plugin.js`** (+ `npm run check:signing`) — seven
assertions over the Gradle transform against a fixture of Expo's real template: injection,
buildType selection, that the *debug* buildType is untouched, that the fallback exists and
warns, idempotency, and that both missing-anchor cases throw. Runs in about a second, in
CI, before anything expensive.

**`.github/workflows/android-build.yml`** — 16 steps. Triggers: push to `main` (artifact,
30-day retention), push a `v*` tag (permanent GitHub Release), manual dispatch with a
chooseable backend URL. Notable choices:

- `concurrency` with `cancel-in-progress`, keyed per ref — without it a slow earlier build
  can finish *after* a faster later one and publish a stale APK as the newest.
- `versionCode = 1000 + github.run_number`. Monotonic per workflow, no committed counter,
  no race; the offset keeps CI builds permanently above local builds, which default to 1.
- Keystore decoded from `ANDROID_KEYSTORE_BASE64` into `$RUNNER_TEMP`, **outside the
  workspace**, so it cannot be swept into an artifact upload. Signing values reach Gradle
  as `-P` properties, never written into `gradle.properties`.
- Interpolated inputs pass through `env:` rather than being expanded straight into shell,
  so a value containing shell metacharacters is data and not code.
- **A signer-certificate check** after the build: `apksigner verify --print-certs` compared
  against a hardcoded `EXPECTED_SIGNER_SHA256`. This is what makes shipping a debug-signed
  APK impossible rather than merely unlikely. Rotating the keystore requires editing that
  constant by hand, on purpose.
- `SENTRY_DISABLE_AUTO_UPLOAD=true`, since no Sentry org/project/auth token is configured
  (ADR-010) and the Gradle hook would otherwise try to upload source maps.

**`ANDROID-BUILDS.md`** — setup walkthrough, the retention model, how signing works and
why it needs a plugin, the three tripwires, local-build instructions, retrieval commands,
a troubleshooting table, and an explicit "deliberately not done yet" list.

**The keystore itself** — `C:\dev\keystores\sarkaritaiyaari-upload.jks`, RSA 4096,
SHA384withRSA, alias `upload`, valid to 2054-01-06. Deliberately **outside the repo**
(`*.jks` is gitignored, but the stronger guarantee is not having it in the tree at all).
Its password is a 24-character random alphanumeric string, given to the user directly and
written to no file inside the repo — this project has already had credentials leak into a
public repo once (see `DEPLOYMENT.md`).

## Real bugs found and fixed

1. **Expo's template has no property-driven release `signingConfig`.** Found by reading the
   actually-generated `mobile/android/app/build.gradle`, not by assuming the well-known
   bare-React-Native `MYAPP_UPLOAD_STORE_FILE` pattern applied. Had that assumption gone
   unchecked, the workflow would have passed `-P` properties that nothing read, produced a
   debug-signed APK, and reported success. This single finding determined the whole design
   (config plugin rather than `-P` flags alone).
2. **`npm ci` failed with `ENOTEMPTY`** on `node_modules/react-native/.gradle/nb-cache` — a
   Gradle cache directory left *inside* `node_modules` by an earlier local build, which npm
   could not remove. Fixed by deleting `node_modules` first, then reinstalling (858
   packages, clean). CI is unaffected since it always starts empty, but it will recur
   locally after any Android build followed by `npm ci`.
3. **The local signed build crashed the Gradle daemon** during
   `expo-module-gradle-plugin:compileKotlin` — *"Gradle build daemon disappeared
   unexpectedly"*. Same class of failure as the one that caused this machine's
   `~/.gradle/gradle.properties` to be written in the first place: Kotlin compiling
   in-process inside a 3 GB daemon on a 16 GB box. A machine constraint, not a workflow
   defect — but it forced a better verification strategy (below) than "run the full build
   once and call it proven".
4. **Two defects in my own first draft of the workflow**, caught by review before pushing:
   `gh release create` rejects `--notes` together with `--generate-notes`, and
   `--notes-start-tag` derived from `git describe` cannot work on the depth-1 shallow
   checkout `actions/checkout` performs by default. Replaced with an explicit
   `gh release view || create / upload --clobber` branch, which also makes re-running a tag
   build idempotent instead of failing on "release already exists".
5. **A false verification claim of my own, corrected.** I reported "typecheck is clean"
   after reading `$?` at the end of a pipeline — which returns `tail`'s exit code, not
   `tsc`'s — while `node_modules` was in fact empty and `tsc` had not meaningfully run. Re-run
   properly afterwards and it genuinely passes. Recorded here because this project's
   verification culture depends on the difference between "watched it work" and "assumed
   it worked", and the same pipeline mistake silently masked the `npm ci` failure too.

## Verified

- **Plugin transform checks:** 7/7 pass (`node scripts/check-release-signing-plugin.js`,
  exit 0), including both throw-on-missing-anchor cases.
- **Workflow YAML parses** via `js-yaml`: triggers `workflow_dispatch` + `push`,
  `concurrency` group `android-apk-${{ github.ref }}` with `cancel-in-progress: true`,
  `permissions: {contents: write}`, 16 steps in the expected order.
- **Typecheck genuinely clean:** `npx tsc --noEmit` → exit 0, zero output lines (re-run
  after the false claim above, with the exit code read directly rather than through a pipe).
- **`app.config.js` resolves correctly** (`npx expo config --type prebuild --json`):
  `ANDROID_VERSION_CODE=1042` → `android.versionCode: 1042`; unset → `1`; `name`,
  `version`, `android.package` preserved from `app.json`; plugin list ends
  `["@sentry/react-native", "./plugins/withReleaseSigning"]`.
- **`expo prebuild --clean` regenerates `android/` and the plugin patches it** — exit 0,
  and reading the generated `app/build.gradle` afterwards shows the `release` signingConfig
  block present inside `signingConfigs`, the release buildType's conditional selection
  present, the **debug buildType untouched**, and `versionCode 1042`.
- **Gradle actually resolves the properties into the signing config.**
  `./gradlew :app:signingReport` with the four `-P` flags → `BUILD SUCCESSFUL`, and:
  ```
  Variant: release
  Config: release
  Store: C:\dev\keystores\sarkaritaiyaari-upload.jks
  Alias: upload
  SHA-256: 90:37:06:A2:D8:D3:EB:97:DC:E5:5D:EC:65:2F:20:35:7B:B7:55:59:6B:21:62:44:E4:E5:3E:60:59:48:68:83
  Valid until: Tuesday, January 6, 2054
  ```
  while `Variant: debug` still resolves to `app/debug.keystore` / `androiddebugkey`. This
  also proves the injected Groovy is syntactically valid, since the project configured.
- **The fallback path works and is loud.** The same task run *without* the `-P` flags →
  `Variant: release / Config: debug / Store: …app\debug.keystore`, and the
  `WARNING: signing this release build with the DEBUG key…` message appears in the output.
- **The signer tripwire works in both directions.** Signed a real APK (an Android SDK
  emulator overlay APK, chosen because it has a genuine binary `AndroidManifest.xml`) with
  the upload key, then ran the workflow's exact extraction pipeline
  (`apksigner verify --print-certs | grep -im1 'certificate SHA-256 digest' | awk '{print $NF}' | tr A-Z a-z`):
  - positive — our key → `903706a2…6883`, matches `EXPECTED_SIGNER_SHA256` → accepted;
  - negative — the APK's original foreign key → `e116fd40…8793` → rejected, which is
    exactly where the build would fail.
- **The fingerprint constant is the right quantity.** `apksigner`'s "certificate SHA-256
  digest" and `keytool`'s "Certificate fingerprint (SHA-256)" were confirmed equal by
  exporting the DER certificate (1324 bytes) and hashing it directly — all three values
  (`sha256(DER)`, keytool, workflow constant) identical. Checked rather than assumed,
  because the whole tripwire rests on it.
- **The keystore opens and holds the key:** `keytool -list` → `PrivateKeyEntry`, alias
  `upload`, `SHA384withRSA`, valid to 2054-01-06.
- **`C:\dev\st` is not inside OneDrive and not a reparse point** —
  `fsutil reparsepoint query` returns `Error 4390: not a reparse point`, and no parent
  directory carries the attribute either. This matters because of the documented
  Files-On-Demand build failure (`manifest 'build.ninja' still dirty after 100 tries`).

## Run #1 on GitHub — failed, and what it taught

Pushed as `f182057`; run #1 failed after 23m15s. Worth recording in full, because two of
the three defects it exposed were mine, not the user's.

**What passed** (so these are now proven on a real Ubuntu runner under JDK 17, not just
locally on Windows/JDK 21): checkout, JDK 17, Node 20, `npm ci`, the plugin checks,
`tsc --noEmit`, build-config resolution, keystore decode, `expo prebuild`, and the
"verify signing config was injected" grep. The config plugin genuinely is portable.

**What failed:** `:app:packageRelease` with
`KeytoolException: Failed to read key  from store ".../upload.jks": keystore password was
incorrect`, caused by `UnrecoverableKeyException` / `BadPaddingException`.

**Real cause: three of the four repository secrets were empty.** The give-away is in the
message itself — `Failed to read key  from store` has *two* spaces where the alias should
be, because AGP formats the alias into that string and the alias was an empty string. A
missing GitHub secret expands to `""` rather than failing, so `-PST_UPLOAD_STORE_PASSWORD=`
and `-PST_UPLOAD_KEY_ALIAS=` were passed empty. `ST_UPLOAD_STORE_FILE` is *not* a secret,
so `project.hasProperty(...)` was still true and the release signingConfig was still
selected — exactly as designed, just with no credentials in it.

**Three defects fixed as a result:**

1. **My workflow validated only one of the four secrets** (`ANDROID_KEYSTORE_BASE64`) and
   none of the other three. The same "fail fast, don't fail silently" reasoning applied to
   the keystore was simply not applied to the passwords. Now all four are checked for
   emptiness *and* the keystore is opened with `keytool` immediately after decoding, so
   wrong credentials cost about a minute instead of 23.
2. **`actions/cache` only saves on success**, so run #1's 23 minutes of native build output
   was discarded and the next run would have started equally cold. Split into
   `cache/restore` + `cache/save` with `if: always()`.
3. **A check I wrote to validate the key password did not work.** `keytool -certreq
   -keypass <wrong>` exits 0 for a PKCS12 keystore — confirmed by actually running it,
   which is the only reason it was caught rather than shipped as false confidence. PKCS12
   has no separate per-key password, so the correct check is that the two secrets are equal,
   guarded on the detected store type. AGP's `getKey(alias, keyPassword)` *does* throw when
   they differ, so the check is worth having.

Also bumped `checkout`/`setup-java`/`setup-node` from v4 to v5 — GitHub's own annotations
flagged them as deprecated and being force-run on Node 24.

The new guard was simulated locally against six inputs — all four correct, run #1's exact
state, a missing alias, a wrong password, a password with a trailing space, and mismatched
key/store passwords — and rejects all five bad cases with a specific message while
accepting the good one.

## Honest gaps

- **No build has yet produced an APK.** Run #1 died at packaging. Steps 12–17 (the actual
  `assembleRelease` completing, the `apksigner` fingerprint check, rename, artifact upload,
  and Release publication) have still never executed anywhere. `gh release create` on a real
  tag also remains completely unexercised.
- **The remaining blocker is entirely on the GitHub side:** three secrets to add. Nothing in
  the repo is known to be wrong any more, but "not known to be wrong" is not "proven right".
- **No full `assembleRelease` ever completed with the upload key.** `signingReport` proves
  the config resolves and the Groovy is valid; it does not prove the APK packaging and
  `apksigner` steps run inside a real Gradle build. The local attempt crashed the daemon on
  a machine memory limit (bug 3), and CI has different memory settings — the project's own
  regenerated `android/gradle.properties` (2 GB heap, parallel on), not this machine's
  3 GB/serial/in-process overrides.
- **The four repository secrets have not been added.** The user must do that; until then
  every run fails fast at the "Decode upload keystore" step by design.
- **The keystore exists in exactly one place.** It is not yet in a password manager or any
  second location. Losing it means no existing install can ever be updated — which for this
  offline-first app means a reinstall costs the user their whole downloaded question bank
  and, if signed out, their entire local history.
- **No AAB, no Play Console upload, no per-ABI split.** TICKET-505 is only half closed.
  Play App Signing is not enabled, so the keystore is currently the *real* signing key
  rather than merely an upload key.
- **No `paths:` filter**, so a backend-only commit still triggers an APK build. Omitted
  deliberately: GitHub applies `paths` to tag pushes too, so a tag on a commit that didn't
  touch `mobile/` would silently produce no release. Wasted free minutes on a public repo
  is the cheaper failure.
- **Sentry source maps are not uploaded**, so release stack traces stay minified.
- **`usesCleartextTraffic: true` is still set** in `app.json` even though the backend is
  now HTTPS. Unrelated to builds, but it is app config that a release build bakes in.
- **Nothing is committed.** Per this project's convention, no commit without an explicit
  request.
