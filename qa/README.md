# QA — requirement-driven manual test management

A git-native, file-based QA system for SarkariTaiyaari: requirements, scenarios, test cases,
executions, defects, test data, and regression suites, each a distinct entity with its own
id, linked by reference rather than nested/duplicated. No database, no dashboard app —
everything here is structured YAML, diffable and reviewable like any other change in this
repo, with a small set of generator scripts producing the traceability matrix and a
dashboard as plain Markdown.

**Status:** the foundational spine — AUTH, CATALOG, QUESTIONS — is fully built through
Phase 8 of the plan below (requirements → scenarios → test cases → suites), with the
execution/defect mechanism established but genuinely empty (no test has actually been run
yet). See `memory/STATUS.md` for the session history and what's next.

## Folder structure

| Path | Contents |
|---|---|
| `requirements/<module>.yaml` | One file per module, a list of requirement records |
| `requirements/_conflicts.md` | Cross-module conflicts, doc-drift, and scoping decisions found during requirement normalization — not itself a requirement source |
| `scenarios/<module>.yaml` | One file per module, a list of scenario records |
| `test-cases/<module>.yaml` | One file per module, a list of test-case **definitions** (never edited by an execution) |
| `test-data/<module>.yaml` | Logical test-data identifiers referenced by test cases — descriptions and provisioning notes only, never a real credential. Generated by `scripts/qa/generate-test-data.js`. |
| `execution/<date>-<module>.yaml` | Append-only execution records. See `execution/README.md`. Empty today — no real execution has occurred. |
| `defects/<module>.yaml` | Starts empty per module; populated only from a real failed execution, never fabricated |
| `suites/*.yaml` | Named lists of test-case ids (Smoke/Sanity/Regression/etc.), generated by `scripts/qa/generate-suites.js` |
| `traceability/RTM.md` | **Generated**, never hand-edited — Requirement → Scenario → Test Case → Execution → Defect |
| `reports/dashboard.md` | **Generated**, never hand-edited — coverage, execution status, automation mapping, priority breakdown |

Generator scripts live in `scripts/qa/` (`generate-test-data.js`, `generate-suites.js`,
`generate-reports.js` — the last produces both the RTM and the dashboard). Run them after
any change to `qa/requirements/`, `qa/scenarios/`, `qa/test-cases/`, `qa/defects/`, or
`qa/execution/` — they are the only source of truth for those two generated files, so a
hand-edit to `RTM.md` or `dashboard.md` will simply be overwritten on the next run.

## ID conventions

`REQ-<MODULE>-NNN`, `SCN-<MODULE>-NNN`, `TC-<MODULE>-NNN`, `INT-<MODULE>-NNN` /
`E2E-<MODULE>-NNN` for cross-system work (not yet built — see "What's not built yet"
below), `EXEC-<MODULE>-NNNN`, `DEF-<MODULE>-NNN`, `TESTDATA-<MODULE>-<NAME>-NN`. Module
codes match the `api/*.md` contract boundaries (`AUTH`, `CATALOG`, `QUESTIONS`, and so on as
later modules are added) — that's the authoritative system-crossing grouping this project
already uses, so the QA repository doesn't invent a second one.

## Entity schemas

**Requirement** (`requirements/*.yaml`): `id`, `feature`, `module`, `system` (list of
Backend/Mobile/Admin), `source_doc` + `source_section`, `description`, `business_rule`,
`actor`, `preconditions`, `inputs`, `expected_outputs`, `validations`, `permissions`,
`dependencies` (other requirement ids), `error_conditions`, `edge_conditions`,
`offline_behavior`, `acceptance_criteria`, `priority`, `status` (Active/Superseded/
Deprecated), `ambiguity` (null, or a `REQUIRES CLARIFICATION: ...` string),
`automation_status`, `automation_hint`.

**Scenario** (`scenarios/*.yaml`): `id`, `requirement_ids` (≥1), `category` (Positive/
Negative/Boundary/Validation/Authorization/Authentication/DataIntegrity/ErrorHandling/
NetworkFailure/Offline/Sync/Performance/Compatibility/Integration/Security/Recovery/
StateTransition/Concurrency/Ambiguous), `title`, `objective`, `systems`, `status`
(Ready/Ambiguous), `notes` (dedup rationale, ambiguity pointer, or null).

**Test case** (`test-cases/*.yaml`, a reusable **definition**, versioned — see below):
`id`, `requirement_ids`, `scenario_id`, `system`, `module`, `feature`, `title`, `objective`,
`preconditions`, `test_data` (a `TESTDATA-*` reference or literal shape description),
`test_environment`, `priority`, `severity`, `test_type`, `steps` (ordered, each with its own
`expected`), `expected_result` (the overall assertion, traced to the requirement),
`actual_result` (**always `""` on a fresh definition**), `status` (**always
`Not Executed`** on a fresh definition), `defect_id` (**always `""`** on a fresh
definition), `remarks`, `automation_status`, `automation_reference`.

**Priority vs. severity** — two different questions, both real fields on every test case:
- `priority` = how soon/how central this is to test (drives suite membership — Critical
  priority is what `sanity.yaml`/`release-gate.yaml` select on).
- `severity` = how bad it is *if this specific check fails* (drives triage once a defect
  exists — a Low-priority edge case can still carry High severity if, when it does fail,
  the consequence is serious).
They usually track together but don't have to — e.g. `TC-AUTH-025` (login-timing safety) is
Medium priority (unlikely to regress, needs special tooling to even check) but Medium
severity too since a real timing leak is a real, if narrow, security exposure; contrast
`TC-CATALOG-047` (badge-fallback rendering) which is Low/Low on both axes.

**Execution** (`execution/<date>-<module>.yaml`, append-only): see `execution/README.md`
for the full schema and rules — this is the one entity type never generated by a script and
never fabricated ahead of a real test run.

**Defect** (`defects/*.yaml`): `id`, `title`, `severity`, `status`
(Open/Fixed/WontFix/Duplicate), `found_in_execution`, `test_case_id`, `requirement_ids`,
`description`, `external_ref` (null today — no external tracker is connected; see
`memory/STATUS.md`'s note that the Atlassian/Jira connector requires authorization this
session doesn't have), `remarks`.

**Test data** (`test-data/*.yaml`): `id`, `type` (Account/Fixture/Value shape),
`description`, `provisioning` (how to set it up per environment — never a literal
credential), `used_by_test_cases` (computed by the generator, not hand-maintained).

**Suite** (`suites/*.yaml`): `suite` (name), `test_case_ids`. Each suite file's own header
comment states its exact membership rule — either a curated explicit list (Smoke) or a
documented mechanical filter over real fields (everything else) — so "why is this test case
in this suite" is always answerable by reading the file itself.

## Core rules this repository follows (binding on every future phase, not just Phase 1)

1. **A requirement is the intended/documented behavior, not "whatever the code currently
   does."** If a source doc and the actual implementation disagree, the requirement is
   extracted from the documented contract, and the drift is recorded as a conflict (see
   `requirements/_conflicts.md`) — never silently resolved by preferring the code.
2. **Source hierarchy**: the relevant `api/*.md` file is authoritative for current contract;
   `reports/*` supply design rationale, history, and known gaps; `reports/architecture-decisions.md`
   explains *why*, and a Superseded ADR never produces an active requirement;
   `reports/open-questions.md` items are explicitly undecided and never become requirements.
3. **Every requirement cites where it came from** (`source_doc`/`source_section`) — nothing
   is invented without a grounding source.
4. **`automation_status` is evidence-based.** `Automated` only when a cited test genuinely
   covers the exact requirement/test case (the test method name is given, and was actually
   read, not guessed at from a class name); `PartiallyAutomated` when coverage is real but
   incomplete; `CandidateForAutomation` for untested backend behavior that could be
   automated; `ManualOnly` for anything with no automated test runner in this project
   (mobile, admin — confirmed to not exist, not just unused) or requiring human/visual
   judgment; `NotSuitable` for something that genuinely can't be automated yet (e.g. the
   REVIEWER-provisioning gap — nothing exists to automate against). Nothing is marked
   Automated on the strength of "a similar test exists."
5. **No real personal data, credentials, or secrets** in any file here — test data uses
   logical identifiers (e.g. `TESTDATA-AUTH-NEW-EMAIL-01`), never a real person's email or a
   real password, and `test-data/*.yaml`'s `provisioning` field describes *how* to create a
   fixture per environment, never a literal reusable value.
6. **Test-case definitions and execution records are separate, and execution is
   append-only** — an execution never overwrites the test case it ran, and a fresh test
   case's `actual_result`/`status`/`defect_id` are always `""`/`Not Executed`/`""`. A test
   case carries an implicit version (see "Versioning" below).
7. **Quality over quantity.** A requirement/scenario/test-case count is never a target. Each
   module's actual count is whatever real requirement/risk coverage needed — see
   `memory/STATUS.md`'s Phase 1–3 session entries for the reasoning behind each module's
   count, and the explicit split/no-split rationale recorded in each test case's own
   `objective`/`remarks` where a scenario became more than one test case.
8. **Ambiguous requirements produce Ambiguous scenarios and test cases that don't pre-assert
   an outcome** — never a guessed pass/fail. A *documented deviation* (known, current,
   disclosed behavior that just happens to look unusual) is different from a *genuinely
   ambiguous* requirement (the intended behavior itself is undecided) — see
   `requirements/_conflicts.md` and the AUTH/CATALOG/QUESTIONS Phase 2/3 reports for worked
   examples of exactly where that line was drawn, case by case.
9. **A gap that isn't yet covered by an approved scenario doesn't get a test case invented
   for it anyway** — the chain is Requirement → Scenario → Test Case in that order; a
   requirement-level or `_conflicts.md`-level finding waits for its own Phase 2 scenario
   before Phase 3 generates anything from it.

## Versioning

A test case's `id` is stable for its life; if its steps/expected result change
substantively, treat that as a new version conceptually (bump a `version` field once one
exists in the live schema — not yet needed since nothing has been re-executed against a
changed definition). Historical execution records always cite `test_case_version`, so a
past Pass/Fail stays interpretable against the definition it was actually run against, even
after the test case itself evolves.

## Regression strategy

Six suites exist today, each with a stated, mechanical-or-curated membership rule (see each
file's own header):

| Suite | Purpose |
|---|---|
| `smoke.yaml` | Hand-curated minimum — "is the system alive" |
| `sanity.yaml` | Critical-priority, determinate-outcome cases — broader than smoke, still fast |
| `regression-full.yaml` | Everything — before a significant, cross-cutting change |
| `regression-<module>.yaml` | Everything in one module — after a change confined to it |
| `release-gate.yaml` | Critical+High, excluding Ambiguous and a short explicit list of hard-to-reproduce-on-demand cases — reliably executable every time, not aspirational |
| `critical-flows.yaml` | The closest current approximation of real end-to-end user journeys, assembled from existing per-module cases — **honestly scoped**: no independent cross-system E2E scenario/test-case pass exists yet (see "What's not built yet") |

## Standing rule (since 2026-09-11): this register grows with every feature, not in separate QA passes

Phases 1-3 (building AUTH/CATALOG/QUESTIONS below) were deliberately done as three separate
review gates — extract requirements, get them reviewed, *then* generate scenarios, *then*
test cases — because that was a one-time bulk build of ~64 requirements from scratch and
needed staged review to keep quality high at that volume. **That staging does not apply
going forward.** Per `AI_RULES.md` §3.21/§5.4, from now on QA coverage is part of building
the feature, not a follow-up phase:

1. **Develop** the feature, change, or fix.
2. **Write its manual test case(s) in this same change** — add/update the requirement in
   `requirements/<module>.yaml` (citing the real source: the `api/*.md` change, the report,
   the task doc), the scenario(s) in `scenarios/<module>.yaml`, and the test case(s) in
   `test-cases/<module>.yaml`, following the schemas above. A fresh test case is always
   `Not Executed` — writing it is the deliverable; running it is a separate, later act.
3. **Automate it if you genuinely can.** If a real automated test can cover the case, write
   it in the same change (today: the backend's `mvn test` suite only — mobile and admin have
   no automated runner, so their cases stay `ManualOnly` until one exists) and set
   `automation_status`/`automation_reference` to the real, verified test method. Never mark
   `Automated` on the strength of "a similar test exists" (see Core rule 4 above).
4. **Regenerate** `traceability/RTM.md` and `reports/dashboard.md`
   (`node scripts/qa/generate-reports.js`) before ending the session, so both stay a true
   reflection of the codebase rather than a stale snapshot.
5. If the change touches a module this register doesn't cover yet (anything beyond AUTH/
   CATALOG/QUESTIONS — see "What's not built yet" below), add that module's
   `requirements/`/`scenarios/`/`test-cases/` files rather than leaving it uncovered.

This is the same discipline already applied to automated tests in this project — a feature
isn't done until its behavior is captured somewhere durable and re-checkable, whether that
check is manual or automated.

## How to add a new requirement

1. Find its authoritative source (an `api/*.md` contract change, a new `reports/<NN>/`
   feature writeup, or a `tasks/TASK-*.md` spec) — never invent one without a citation.
2. Add it to the right `requirements/<module>.yaml` with the next sequential id, filled in
   per the schema above. If it's genuinely ambiguous, say so in `ambiguity` rather than
   guessing.
3. Cross-check it against `requirements/_conflicts.md` and any Superseded ADR/open-question
   before treating it as Active.
4. Generate its scenario(s) and test case(s) in the same change per the standing rule
   above — the old "separate Phase 1/2/3 passes" note applied only to this register's
   initial bulk build (see `memory/STATUS.md`'s session history for why that staging
   mattered at that scale, e.g. the REVIEWER-role finding), not to day-to-day feature work.

## How to review a test case before trusting it

Ask, in order: does it actually come from a requirement (not an implementation detail)? Is
the expected result traceable to that requirement's own `acceptance_criteria`/
`error_conditions`/`edge_conditions`? Can it be executed independently of any other test
case's state? Does another test case already cover this (check the linked scenario's
`notes` and the module's own Phase 3 report for documented dedup decisions)? Is every
important condition covered without inflating the count? Could another QA engineer execute
it without asking the author a clarifying question? Can you trace it all the way back to a
requirement id? Will it stay meaningful if the UI/implementation changes but the
requirement doesn't?

## How to record a real execution

See `execution/README.md` in full. In short: append to (or create) today's
`execution/<date>-<module>.yaml`, never edit an existing execution file or the test case's
own definition; record what actually happened, including for Ambiguous cases (there's no
guessed expectation to compare against, just an honest observation); then regenerate the
RTM/dashboard.

- **Every other module** beyond AUTH/CATALOG/QUESTIONS — the rest of `api/*.md`'s contract
  surface (question groups, question intelligence/ingestion, exam intelligence, exam guide,
  weakness radar, AI admin), plus mobile-app-only and admin-console-only behavior not
  reachable through a documented API contract, is entirely unscoped.
- **Real cross-system INT-/E2E- scenarios and test cases** — `critical-flows.yaml` is an
  honest approximation assembled from existing per-module cases, not a genuine independent
  scenario-design pass across module boundaries. That would need its own Phase 2/3 work.

  has actually been run against a live environment yet.
- **External defect-tracker integration** (e.g. Jira) — `defect.external_ref` exists as a
  field for this but nothing is wired up; the Atlassian connector available in this
  environment needs authorization this session doesn't have.

## AI-assisted QA capabilities — design only, nothing built (Phase 11)

The schema above was deliberately built to make a future AI-assisted maintenance pass
cheap, not to require new infrastructure first:

- **Generating scenarios/test cases from a new requirement**: point a session at one
  `requirements/<module>.yaml` entry plus this README's schema and rules — the same prompt
  shape this project's own Phase 1→2→3 sessions already used, just scoped to one
  requirement instead of a whole module.
- **Detecting duplicate/overlapping coverage**: every scenario/test case already declares
  its `requirement_ids`; a script (or an AI pass) can group by requirement and flag two
  scenarios/test cases whose `objective`/`steps` are suspiciously similar for human review —
  the `notes`/`remarks` fields this repo already uses to explain *deliberate* overlap
  (e.g. `SCN-AUTH-008`, `TC-CATALOG-052`) are exactly the signal that would let such a check
  distinguish "explained" from "actually redundant."
- **Detecting missing coverage**: `scripts/qa/generate-reports.js` already computes
  requirements-with-zero-scenarios programmatically (see the RTM's own summary section) —
  extending it to flag a *new* requirement added to a `requirements/*.yaml` file with no
  matching scenario yet is a small addition to an already-existing script, not new
  infrastructure.
- **Analyzing failed executions / identifying regression candidates**: once
  `execution/*.yaml` has real data, a query over "which test cases failed in the last N
  executions" or "which requirement's test cases fail most often" is a direct read of
  already-structured data — no new schema needed.
- **Mapping requirements to existing (code) automated tests, and flagging impacted tests
  after a requirement changes**: `automation_hint`/`automation_reference` already record
  the *specific* backend test method believed to cover each requirement/test case; keeping
  that mapping current as backend tests are added/renamed is a natural
  requirement-file-adjacent task, not a new capability.
- **Comparing a requirement change against its existing test cases**: since every
  scenario/test case cites `requirement_ids` and every requirement cites `source_doc`, a
  diff on a requirement's `acceptance_criteria` can be mechanically joined against exactly
  the scenarios/test cases that need re-review — again, no new schema, just a read.

None of the above is implemented now, per the explicit instruction not to build every AI
capability up front — this section exists so the *next* phase of work (whenever it happens)
starts from "here's how the existing structure already supports this" rather than
re-deriving it.
