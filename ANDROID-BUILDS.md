# Android Builds — GitHub Actions

Signed release APKs are built by GitHub Actions, not by hand. The workflow is
[`.github/workflows/android-build.yml`](.github/workflows/android-build.yml).

| Trigger | Produces | Kept for |
|---|---|---|
| Push to `main` | APK as a **workflow artifact** | 30 days, then auto-deleted |
| Push a tag `v*` | APK attached to a **GitHub Release** | **Forever** |
| Manual run (*Actions → Android APK → Run workflow*) | APK as an artifact, with a chooseable backend URL | 30 days |

Artifacts expire, Release assets don't. That's the whole retention model: disposable
builds while developing, and a permanent archive only for versions you deliberately name.

**To keep a build forever, tag it:**

```bash
git tag v1.0.1
git push origin v1.0.1
```

### 2. Add four repository secrets

*GitHub → Settings → Secrets and variables → Actions → New repository secret*

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | the keystore, base64-encoded (see below) |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password |
| `ANDROID_KEY_ALIAS` | `upload` |
| `ANDROID_KEY_PASSWORD` | same as the keystore password |

To regenerate the base64 at any time:

```bash
base64 -w0 /c/dev/keystores/sarkaritaiyaari-upload.jks
```

Paste the whole single line, with no trailing newline and no wrapping.

### 3. Optionally set the backend URL

*Settings → Secrets and variables → Actions → Variables → New repository variable*

`API_BASE_URL` — for example
`https://sarkaritaiyaari-backend-815653276881.asia-south1.run.app/api`

Not a secret; it's already in committed docs. If unset, the workflow falls back to the
default hardcoded in its `env:` block. A manual run can override it per build.

**The `/api` suffix is required** — `mobile/src/api/client.ts` appends paths like
`/exams` directly.

## How signing works, and why it needs a plugin

`mobile/android/` is **not committed**. It's regenerated by `expo prebuild` on every
build (Continuous Native Generation), so anything edited inside it is discarded. And
Expo's template hardcodes the release build to use the *debug* key:

```gradle
release {
    // Caution! In production, you need to generate your own keystore file.
    signingConfig signingConfigs.debug
}
```

Unlike the bare React Native template, Expo's provides no property-driven release
signingConfig to hook into. So the only durable place to make this change is a config
plugin, which runs *during* prebuild:
[`mobile/plugins/withReleaseSigning.js`](mobile/plugins/withReleaseSigning.js), registered
via [`mobile/app.config.js`](mobile/app.config.js).

The keystore reaches Gradle as command-line properties (`-PST_UPLOAD_STORE_FILE=…`), and
the decoded `.jks` is written to `$RUNNER_TEMP`, outside the workspace. Nothing secret is
ever written into the repo or into `gradle.properties`.

### Three tripwires against shipping a debug-signed APK

A debug-signed APK installs perfectly and looks completely normal. It just can't be
distributed, and can't upgrade a properly signed install. The README already lists this
as a known trap, so the workflow checks for it three times:

1. **`scripts/check-release-signing-plugin.js`** — asserts the Gradle transform's logic
   and its failure modes. Runs in seconds, before anything expensive.
2. **A grep after prebuild** — confirms the patch actually landed in the generated
   `build.gradle`. The plugin also *throws* rather than silently skipping if Expo's
   template shape has changed.
3. **`apksigner verify --print-certs`** — compares the finished APK's real signer
   certificate against `EXPECTED_SIGNER_SHA256` in the workflow. This is the one that
   matters; the first two can only fail earlier and more cheaply.

If you ever rotate the keystore, `EXPECTED_SIGNER_SHA256` must be updated by hand. That's
intentional: a signing-key change should never be able to happen silently.

## versionCode

Android requires `versionCode` to strictly increase — two builds sharing one value can't
both be installed, and Play rejects a repeat.

```
versionCode = 1000 + github.run_number
```

`run_number` is monotonic per workflow, so there's no counter to commit and no race. The
`1000` offset keeps CI builds permanently above local builds, which fall back to `1`.

`versionName` comes from `app.json`'s `expo.version`, and can be overridden for one build
with the `ANDROID_VERSION_NAME` env var.

## Local builds still work

The debug fallback is intact, so the existing flow is unchanged:

```bash
cd mobile
export EXPO_PUBLIC_API_BASE_URL="http://10.0.2.2:8080/api"
npx expo prebuild --platform android --no-install --clean
cd android && ./gradlew assembleRelease
```

That produces a **debug-signed** APK and Gradle prints a loud warning saying so. To build
a properly signed one locally, pass the same properties CI does:

```bash
./gradlew assembleRelease \
  -PST_UPLOAD_STORE_FILE=/c/dev/keystores/sarkaritaiyaari-upload.jks \
  -PST_UPLOAD_STORE_PASSWORD=<password> \
  -PST_UPLOAD_KEY_ALIAS=upload \
  -PST_UPLOAD_KEY_PASSWORD=<password>
```

**Don't build from inside OneDrive.** Files-On-Demand touches files mid-build, leaving
CMake regenerating forever and ninja failing with
`manifest 'build.ninja' still dirty after 100 tries`. A directory junction does not help —
Windows resolves it back to the real path. `C:\dev\st` is deliberately outside OneDrive.

## Retrieving an old build

```bash
gh run list --workflow=android-build.yml   # recent builds
gh run download <run-id>                   # fetch one (arrives as a .zip)

gh release list                            # permanent versions
gh release download v1.0.1 --pattern '*.apk'
```

Or through the web UI: the run's page for artifacts, the Releases page for tagged
versions.

Note that **deleting a workflow run also deletes its artifacts**. Releases are unaffected.

## Troubleshooting

| Symptom | Cause |
|---|---|
| No run appeared at all | Pushed to a branch other than `main`. GitHub doesn't report a skipped trigger — the run simply never exists. |
| `Missing or empty repository secret(s): …` | Exactly what it says — that secret doesn't exist under **Repository secrets**, or its name differs. A missing GitHub secret expands to an *empty string*, not an error, so the workflow checks all four explicitly. |
| `Cannot open the keystore with ANDROID_KEYSTORE_PASSWORD / ANDROID_KEY_ALIAS` | Usually a trailing space or newline pasted into the password secret, a wrong alias (this keystore uses `upload`), or truncated base64. |
| `keystore password was incorrect` / `BadPaddingException` inside `:app:packageRelease` | **This is what a missing password secret used to look like** — and it appeared only after 20+ minutes of building. Run #1 failed this way. The keystore is now verified with `keytool` immediately after decoding, so this should never surface from the build itself again. If it does, the store and key passwords genuinely differ. |
| `ANDROID_KEYSTORE_BASE64 is not valid base64` | The value has spaces or line breaks in it. Re-copy it as one single line. |
| `APK is signed by an unexpected certificate` | The keystore secrets don't match the keystore the fingerprint came from. Re-check all four, then `EXPECTED_SIGNER_SHA256`. |
| `withReleaseSigning did not patch build.gradle` | An Expo SDK upgrade changed the template. Update the anchor constants in the plugin. |
| Builds but the app can't reach the backend | `EXPO_PUBLIC_API_BASE_URL` is baked in at bundle time. Wrong value, missing `/api` suffix, or `localhost` — which on a phone means the phone itself. |
| Works locally, fails in CI | Linux is case-sensitive and Windows isn't. `import './Foo'` for `foo.ts` passes locally and breaks on the runner. |
| Two pushes, older APK published last | Shouldn't happen — `concurrency` with `cancel-in-progress` cancels the superseded run. If it does, that block was removed. |

## Deliberately not done yet

- **No AAB.** Play requires an `.aab`; this builds an installable `.apk`. Add a
  `bundleRelease` step when TICKET-505 (Play Console) is picked up.
- **No Play Console upload.** Also TICKET-505. When you get there, turn on **Play App
  Signing** — Google then holds the real signing key and this keystore becomes only an
  *upload* key, so losing it becomes a reset rather than a dead end.
- **No per-ABI split.** One universal APK, so it's larger than it needs to be.
  `--split-per-abi` roughly halves the download.
- **No Sentry source-map upload.** `SENTRY_DISABLE_AUTO_UPLOAD=true` is set because no
  Sentry org/project/auth token is configured (ADR-010). Stack traces stay minified until
  that exists.
- **No `paths:` filter.** A backend-only commit still triggers a build. Filtering was
  skipped on purpose: `paths` applies to tag pushes too, so a tag on a commit that didn't
  touch `mobile/` would silently produce no release. Wasting free minutes on a public
  repo is the cheaper mistake.
- **No OTA updates.** EAS Update would let JS-only changes ship without a build at all,
  removing most of the reasons to run this workflow. Worth considering separately.
- **`usesCleartextTraffic` is still enabled** in `app.json`. The backend is HTTPS now, so
  this can probably be removed — but that's an app-config change, not a build change.
